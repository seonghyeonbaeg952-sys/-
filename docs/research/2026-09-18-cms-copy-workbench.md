# CMS 문구 찾기·바꾸기 작업대 조사와 설계

조사일: 2026-09-18. 대상: 한글·Word/PPT는 사용하지만 웹사이트 구조나 CMS 키 이름은 모르는 운영자. 이 문서는 **공식 문서 조사와 설계 제안**이며 구현 완료 또는 실제 사용자 테스트 결과가 아니다.

## 1. 조사 계획과 실제 범위

목표: 운영자가 문구의 위치를 몰라도 찾아서, 바뀌는 범위를 이해하고, 실수했을 때 복구할 수 있는 편집 흐름을 만든다.

연구 질문:

1. 문서 편집기의 찾기·다음 찾기·바꾸기 중 어떤 상호작용이 웹 CMS에서도 익숙하고 안전한가?
2. 현재 페이지와 전체 홈페이지, 공통 문구와 기기별 문구를 어떻게 구분해야 잘못 바꾸지 않는가?
3. 여러 곳을 바꿀 때 원문·부분 서식·다른 작업자의 변경을 어떻게 보호하는가?
4. 검색 패널과 실제 화면, 플로팅 글꼴 창을 동시에 써도 선택과 키보드 포커스를 잃지 않는가?
5. 작은 화면·보조기기·한글 입력 중에도 조작 의도가 유지되는가?

방법: Microsoft, 한컴, Figma, CKEditor, Tiptap, W3C의 공식 문서 데스크리서치 + 현재 `EditorCopyPanel.tsx`의 검색·선택 흐름 읽기 + Figma 시각 검증. 이번 조사에 참가한 실제 운영자는 **0명**이다. 향후 초보 운영자 3–5명에게 아래 과제를 관찰하는 것이 필요하지만, 수행하지 않은 사용자 조사를 했다고 보고하지 않는다.

**실제 확인한 고유 공식 본문은 14개**다. 검색 결과, 번역판, 동일 URL 재열기, 다른 날짜의 기존 연구 문서를 중복 집계하지 않았다. 수천·수만 개 조사 주장은 하지 않는다. 한컴 ‘선택 사항’ 문서는 한 차례 메타데이터 조회 후 본문 재조회가 타임아웃되어 이 14개에 넣지 않았다.

## 3. 공통 패턴과 그대로 가져오지 않을 동작

공통성이 높은 패턴은 ‘찾을 내용/바꿀 내용’, 이전/다음, 결과 수, 현재 결과 강조, 한 건 바꾸기, 범위를 한정한 일괄 변경, 명시적인 닫기다. Word·한/글은 문서 안의 기능이고 이 CMS는 여러 소유 페이지·기기 문서·공개 상태가 있으므로, 파일 검색과 홈페이지 게시를 같은 동작으로 만들면 안 된다.

- 한/글 H3의 찾아 바꾸기 키는 Ctrl+F2/Ctrl+Q,A이며 Word의 Ctrl+H와 다르다. 브라우저 Ctrl+H는 방문 기록과도 겹칠 수 있으므로 ‘Office 공통 단축키’라고 단정하지 않는다.
- 검색어/결과 탐색이 `CanvasSelection`을 바꾸어 플로팅 서식 대상까지 바꾸지 않도록 한다. ‘화면에서 선택’ 또는 ‘편집’이 별도 명시 동작이다.
- 정규표현식·와일드카드는 첫 화면에 넣지 않는다. 현재 요구는 문구 관리이며, 잘못된 패턴·치환 기호·실행 비용까지 늘리는 전문가 도구는 별도 검증 전 제외한다.
- 모든 결과를 자동 선택하거나 여러 페이지의 모든 기기를 기본 치환 범위로 잡지 않는다.
- 공개 홈페이지의 레이아웃·폰트·색·DOM 기본값은 변경하지 않는다. 검색 강조와 편집 경계는 CMS 미리보기 안에서만 표시한다.

## 5. 첫 구현의 범위

**찾기는 전체 홈페이지**, **바꾸기는 명시한 한 페이지·한 범위**로 시작한다. 이 정책은 기술적 한계를 숨기는 것이 아니라 서로 다른 서버 문서의 부분 성공을 피하는 보수적 기본값이다. 전체 페이지 일괄치환은 서버 트랜잭션·충돌·감사·복구까지 구현된 뒤 별도 확장한다.

1. `문구 찾기` 버튼 → 검색 패널을 열고 찾을 내용에 포커스.
2. 검색 범위: 현재 페이지/전체 페이지. 결과에는 페이지, 화면 위치, 문구명, 값 출처와 앞뒤 문맥.
3. 결과 클릭은 해당 문구 정보만 선택한다. `화면에서 보기` 또는 `편집`으로 실제 캔버스 조작에 진입.
4. `바꾸기`를 펼치면 바꿀 내용과 적용 범위를 다시 표시.
5. `이 곳만 바꾸기` 또는 `변경 미리보기` 선택.
6. 미리보기에서 항목별 전/후·체크 상태·서식 유지 여부 확인.
7. 적용은 로컬 초안 변경이며 공개하지 않는다. 같은 작업 전체를 한 번에 되돌릴 수 있어야 한다.
8. 기존 `임시저장 → 변경 확인·게시`를 그대로 사용한다.

## 6. 일괄 치환 데이터 계약

- 대상을 `(ownerPage, scope, key)`로 중복 제거한다. 렌더링된 DOM 출현 횟수와 저장 필드 수는 다르다.
- 미리보기 생성 당시 문자열·부분 서식·리비전 또는 버전 지문을 보관한다. 적용 전 전부 재확인한다.
- 하나라도 충돌하면 선택된 전체 치환을 중단하고 입력·검색어·선택을 보존한다. 조용히 일부만 성공시키지 않는다.
- 원본 전체 문자열에서 안전한 위치만 수정한다. 숨겨진 접두/접미, 나머지 글자의 부분 서식은 보존하고 길이 변경에 따라 범위를 이동한다.
- 치환으로 삽입한 문자를 다시 검색해서 같은 작업에서 연쇄 치환하지 않는다. 검색 결과 스냅샷 기준으로 한 번씩 처리한다.
- 대체값의 `$1`, `$&`, HTML은 평문이다. 매크로/정규식 치환 표현식/임의 HTML로 실행하지 않는다.
- 빈 검색어, 같은 문자열로 치환, 0건, 초과 길이, 필수 문구 삭제는 상태와 이유를 명확히 표시한다.
- 한글 IME 조합 중에는 확정 검색·치환·패널 닫기 단축키를 실행하지 않는다. 편집 중인 캔버스 버퍼가 있으면 먼저 마치도록 안내한다.
- URL·boolean·number·동적 CMS 값은 일반 문자열 일괄치환의 기본 대상에서 제외한다. 필요한 수정 화면으로 이동한다.
- 서버 반영 전 권한·카탈로그·스키마 검증은 기존 경로에서 다시 수행한다. 검색 결과나 iframe 메시지만으로 쓰기 권한을 부여하지 않는다.

## 7. 검증 과제와 완료 기준

실제 초보 운영자 관찰 과제(아직 수행 전): ‘어느 페이지인지 모르는 입단 안내 찾기’, ‘모바일 문구만 수정’, ‘같은 단어 두 곳 중 한 곳만 변경’, ‘잘못 바꾼 것을 원문과 비교해 복구’, ‘게시하지 않고 작업 종료’. 사용자 3–5명에게 설명 없이 시도하게 하고 성공 여부·실수·도움 요청을 기록한다. 가상의 성공률은 만들지 않는다.

구현 자동/수동 검증:

- 검색: 입력→결과→이전/다음→0건→초기화; 전체 페이지 중 로딩 실패가 결과 없음으로 오인되지 않음.
- 선택: 검색 강조와 글자 선택이 독립적; 검색 패널 클릭 때문에 입력·캐럿·서식을 잃지 않음.
- 치환: 한 건/여러 건/중복 소스/겹친 일치/결합문자/이모지/한글 조사/영문 대소문자/앞뒤 줄바꿈.
- 안전: 미리보기 뒤 원본 수정·타 기기 수정·권한 만료·네트워크 실패·중복 클릭·부분 저장 실패.
- 복구: 단일 치환과 일괄치환 한 번에 되돌리기; 새 입력 후 재실행 분기 종료; 초기화는 필터만 초기화.
- 접근성: 키보드·포커스 복귀·결과 상태 낭독·검색 필드 라벨·44px 프로젝트 터치 기준·확대 화면. 도구 수가 늘어도 본문 가독성을 유지.
- 반응형: 1440px 나란히 패널, 768px 접을 수 있는 패널, 390px 한 작업씩 전환하는 패널. 좁은 화면에서 글꼴창과 검색창을 동시에 겹쳐 놓지 않음.
- 공개 디자인: 미리보기 밖에 검색용 래퍼·색 강조·스타일이 남지 않고, 초안만 변경한 상태에서 방문자 화면이 변하지 않음.

### 실제 수행한 시각·구조 검증

- 새 시안 6개를 Figma 스크린샷으로 확인했다. 작업대는 1440px와 390px에서 따로 검토했다.
- 모바일 검토의 전후 문구를 별도 줄로 조정해 부자연스러운 단어 중간 줄바꿈을 줄였다.
- 6개 루트에서 가로 경계를 벗어나는 보이는 노드가 **0개**임을 API로 검사했다. 데스크톱 홈페이지 미리보기는 의도적인 세로 스크롤/클리핑 영역이다.
- 실제 편집 도구 패널 6개에서 부모 아래로 넘치는 직접 자식 **0개**, 높이 44px 미만 버튼 인스턴스 **0개**, 남은 제작 중 placeholder **0개**를 확인했다.
- 모바일 검토는 데스크톱 720px 오버레이가 아니라 별도 390px 프레임으로 연결되어 있다.
- 원래 플로팅 시안의 이름과 크기(1440×1040 / 390×980)를 재확인했고, 이번 쓰기 호출은 새 시안의 노드만 수정했다.
- 실제 CMS 코드·DB·권한·서버 저장은 이 디자인 작업에서 변경하거나 테스트하지 않았다. 기능 검증은 구현 담당 작업의 테스트 결과와 구분해야 한다.

### 남은 검증

초보 운영자 관찰, 실제 CMS 키보드/IME/스크린리더/네트워크 실패/부분 서식 보존/되돌리기 검증은 별도 구현 단계의 과제다. 이번 시안에서는 별도의 768px 태블릿 프레임을 추가하지 않았으며, 기존 태블릿 편집 시안과 실제 반응형 동작을 함께 확인해야 한다.
