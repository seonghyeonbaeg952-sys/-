# 서울모테트청소년합창단 홈페이지 PRD

제품 요구사항 정의서 · 버전 1.1 · 갱신일 2026년 9월 17일

> 9월 17일 CMS 개선의 상세 현황은 [CMS 개선 결과](cms-audit-results.md), [운영자 설명서](cms-operator-guide.md), [전체 계획](superpowers/plans/2026-09-17-cms-comprehensive-overhaul.md)를 함께 참조한다. 아래 기존 기능 명세 전체를 최신 운영 검증 완료로 간주하지 않는다.

## 1. 문서 목적과 기준

이 홈페이지는 서울모테트청소년합창단의 활동과 교육 방향을 소개하고, 공연 관람·입단 지원·후원·문의로 연결하는 공식 채널이다. 운영자는 관리자 CMS에서 콘텐츠와 접수 업무를 관리한다.

이 문서는 현재 로컬 작업트리에 구현된 기능을 제품 요구사항으로 정리한다. 운영자, 디자이너, 개발자가 같은 기준으로 유지보수와 후속 개발을 판단하는 데 사용한다. 새 디자인 적용이나 데이터 변경을 승인하는 문서는 아니다.

### 1.1 확인 수준

| 표기 | 의미 |
| --- | --- |
| 코드 확인 | 현재 라우트·컴포넌트·데이터 처리 코드에서 구현을 확인했다. 모든 브라우저에서 검증했다는 의미는 아니다. |
| 실행 확인 | 이번 문서 작성 과정에서 명령 또는 읽기 전용 요청을 실행하고 결과를 확인했다. |
| 운영 기록 | 저장소에 남아 있는 과거 적용·검증 기록이다. 이번 검증과 구분한다. |
| 후속 요구 | 제품 기준으로 필요하지만 현재 구현 완료로 간주하지 않는 항목이다. |
| 확인 필요 | 운영 정책, 실제 배포 환경, 실제 화면 동작을 추가 확인해야 하는 항목이다. |

현재 작업트리에는 기존의 미커밋 수정이 있다. 따라서 이 PRD는 특정 배포 버전이나 Git 커밋의 명세가 아니라, 기준일의 로컬 구현 명세다. 코드와 원격 운영 데이터가 같다고 가정하지 않는다.

### 1.2 문서 적용 원칙

- 본문의 요구사항은 유지해야 할 제품 계약이다. 현재 동작과 요구사항 사이의 차이는 13절에 기록한다.
- 승인된 인명·경력·본문은 임의로 재작성하지 않는다. CMS 운영 정보가 디자인용 예시보다 우선한다.
- 기능 추가, 디자인 변경, DB 마이그레이션은 별도 작업으로 검토한다.
- 기능 또는 데이터 계약을 변경할 때 관련 요구사항 ID, 검증 기준, 문서 변경 이력을 함께 갱신한다.

## 2. 제품 목표와 범위

### 2.1 해결할 문제

1. 방문자가 합창단 소개, 공연 일정, 입단 방법, 연락처를 여러 채널에서 찾아야 하는 불편을 줄인다.
2. 운영자가 사진·포스터·안내문 수정마다 개발자에게 의존하지 않도록 한다.
3. 입단지원, 일반 문의, 후원약정을 별도 업무로 구분해 접수 누락과 혼동을 줄인다.
4. 청소년 단원의 공개 범위를 보호하면서 현재와 이전 활동을 하나의 기록으로 소개한다.
5. 포스터와 사진의 비율, 날짜 가독성, 모바일 조작성을 유지하면서 합창단의 시각적 정체성을 표현한다.

### 2.2 목표

| 목표 | 사용자가 얻는 결과 | 판단 기준 |
| --- | --- | --- |
| 공식 정보 탐색 | 합창단·공연·입단 정보를 스스로 찾는다. | 메뉴에서 해당 상세 화면까지 이동 가능하다. |
| 안전한 입단 접수 | 필수 정보를 확인하고 신청을 제출한다. | 서버가 확인한 접수만 성공으로 표시한다. |
| 운영 자립 | 승인된 콘텐츠를 CMS에서 수정한다. | 재배포 없이 연결된 공개 화면에 반영된다. |
| 개인정보 보호 | 접수 내용과 비공개 단원 정보가 공개되지 않는다. | UI뿐 아니라 API·DB·Storage 권한으로 보호된다. |
| 기록 활용 | 공연, 공지, 사진, 영상, 포스터, 연혁을 탐색한다. | 빈 자료와 오류를 구분하고 목록·상세 이동이 가능하다. |

### 2.3 포함 범위

- 공개 홈페이지: 홈, 합창단 정신, 합창단 소개, 지휘자·반주자·단원, 연혁.
- 공연 목록·상세, 공지사항 목록·상세, 사진·영상·포스터 갤러리.
- 입단 안내, 모집 기간, 입단지원서 v2, FAQ.
- 후원 안내와 약정, 후원사, 일반·공연·입단 관련 문의, 오시는 길.
- 관리자 로그인, 콘텐츠 관리, 접수 상태·메모 관리, 공개 여부·순서·이미지 관리.
- 반응형 레이아웃, 기본 SEO, 로딩·오류·빈 상태, 접근성 및 모션 감소 대응.

### 2.4 현재 범위에 포함하지 않는 기능

- 일반 방문자 회원가입·마이페이지·신청 내역 로그인 조회.
- 단원 전용 출결, 회비, 악보, 수업 또는 학사 관리.
- 자체 티켓 판매·좌석 선택·결제·환불. 현재 공연 예매·신청은 외부 URL 연결이다.
- 후원금 자동 결제·자동이체·입금 확인·기부금 영수증 자동 발급.
- 문의 답변 자동 이메일, 문자, 카카오 알림 발송.
- 다국어 사이트, 통합 CRM, 공개 게시판, 실시간 채팅.
- 모든 페이지를 자유롭게 배치하는 노코드 페이지 빌더. CMS는 정해진 콘텐츠 필드를 편집한다.

## 3. 사용자와 핵심 흐름

| 사용자 | 주요 목적 | 대표 흐름 |
| --- | --- | --- |
| 일반 방문자·관객 | 합창단과 공연 확인 | 홈 → 공연 목록 → 공연 상세 → 포스터 확대 또는 외부 예매 |
| 입단 희망자·보호자 | 조건 확인과 지원 | 입단 안내 → 대상·절차·연습·FAQ → 지원서 → 제출 전 확인 → 접수 결과 |
| 후원 희망 개인·기업 | 후원 방법 확인 | 후원 안내 → 개인·기업 선택 → 약정 작성·인쇄 또는 문의 |
| 공연 의뢰자 | 의뢰 전달 | 후원·문의 → 공연 관련 문의 → 입력·동의 → 접수 |
| 관리자 | 콘텐츠 운영과 접수 처리 | 로그인 → 권한 확인 → 업무 메뉴 → 수정·저장 → 공개 화면 또는 처리 상태 확인 |

### 3.1 콘텐츠 게시 흐름

관리자 로그인 → 대상 콘텐츠 등록·편집 → 이미지·본문·날짜 확인 → 공개 여부·순서 설정 → 저장 응답 확인 → 공개 화면 재조회 → 공개 결과 확인.

임시 입력, 저장 완료, 공개 여부는 서로 다른 상태다. 저장되지 않은 입력이 공개되었다고 안내하지 않는다. 현재 CMS에는 별도의 다단계 결재·승인 워크플로가 없으므로 운영자가 공개 전 내용을 검수한다.

### 3.1.1 문구·디자인 편집의 추가 게시 흐름

`홈페이지 편집 · 미리보기`는 화면/기기 선택 → 수정 → 실제 페이지 미리보기 → 임시저장 → 변경 확인 → 해당 화면 게시 순서다. 과거 게시본은 초안으로 복원하고 재게시를 별도로 선택한다. 다른 관리자와 같은 버전을 저장할 때 덮어쓰기를 거부하며 입력을 유지한 비교 절차를 제공한다. 원본 공연/프로필/모집/후원 콘텐츠는 기존 전용 CMS가 계속 원본이며, 그 저장 계약을 초안 게시로 바꾼 것은 아니다.

### 3.2 신청과 문의의 구분

입단 관련 질문은 `contacts` 문의로, 실제 입단지원서는 `join_applications`로, 후원약정은 `support_pledges`로 저장한다. 문의 접수 성공을 입단지원 완료나 후원금 납부 완료로 표현하지 않는다.

## 4. 정보 구조와 URL

### 4.1 공개 홈페이지

| 화면 | URL | 핵심 기능 |
| --- | --- | --- |
| 홈 | `/` | 대표 이미지, 소개, 입단 연결, 공연·공지, 정신, 아카이브, 후원 연결 |
| 합창단 정신 | `/spirit` | 교육 철학·가치·정신과 관련 내용 |
| 합창단 소개 | `/about`, `/about?section=overview` | 기본 소개와 정신 요약 |
| 소개 전체 | `/about?section=all` | 소개 하위 콘텐츠를 연속 표시 |
| 지휘자 | `/about?section=conductor` | 프로필·공연 사진과 약력 |
| 반주자 | `/about?section=accompanist` | 인물별 사진·학력·활동 |
| 단원 | `/about?section=members` | 현재·이전 활동을 포함한 명단과 필터 |
| 연혁 | `/about?section=history` | 연도 탐색과 기록 펼침 |
| 공연 목록 | `/concerts?filter=upcoming`, `filter=past`, `filter=all` | 기간·연도·분류·검색 |
| 공연 상세 | `/concerts/:concertId` | 일시·장소·포스터·본문·프로그램·출연·외부 링크 |
| 공지 목록 | `/notices` | 중요 공지·분류·검색 |
| 공지 상세 | `/notices/:noticeId` | 공지 본문과 목록 복귀 |
| 갤러리 | `/gallery?tab=photos`, `tab=videos`, `tab=posters` | 분류, 이미지 확대, 영상 재생 |
| 입단 안내 | `/join` | 대상·절차·연습·FAQ |
| 입단 세부 안내 | `/join?section=eligibility`, `process`, `practice`, `faq` | 지정 항목 탐색 |
| 입단지원서 | `/join?section=contact#application` | 필수 응답·확인·제출 |
| 후원·문의 | `/contact` | 문의, 후원, 후원사, 위치 정보 |
| 후원 안내 | `/contact?section=support` | 후원약정·관련 문의 |
| 후원사 | `/contact?section=sponsors` | 공개 동의한 후원사 |
| 문의 | `/contact?section=performance` | 유형별 문의 접수 |
| 오시는 길 | `/contact?section=location` | 주소·연락처·교통·지도 |
| 관리자 로그인 | `/admin/login` | 관리자 인증 |

호환 경로 `/contact?section=join`은 새 입단지원서로 이동한다. `/about?section=spirit`는 별도 탭을 만들지 않고 소개 화면으로 해석한다. 잘못된 소개 섹션 값은 기본 소개로, 잘못된 갤러리 탭 값은 사진으로 처리한다.

현재 `/`는 `HomeV4ProductionPage` → `HomeRoute` → `HomePage`로 연결된다. 파일 이름에 `sample`이 포함되어도 실제 루트 화면의 일부다. 반면 `/home-classic`, `/home-hero-intro-sample`, `/home-section-flow-sample`, `/spirit-hero-sample` 등은 일반 방문자 주요 메뉴와 구분되는 기존·샘플 경로다. 샘플 경로의 배포 노출 정책은 별도 확인한다.

### 4.2 URL 상태 계약

- 공지: `q`, `category`, `filter=important`를 사용하고 상세 이동 시 목록 조건을 전달한다.
- 갤러리: `tab`, `category`, `media`로 현재 자료와 확대 대상을 표현한다. 필터 변경 시 열린 자료를 정리한다.
- 공연: 현재 `filter`만 URL 상태이고 검색·분류·연도는 화면 내부 상태다. 모든 조건이 새로고침 후 복원된다고 가정하지 않는다.
- 입단지원서의 입력값은 URL에 넣지 않는다. 현재 페이지 메모리에 유지되며 브라우저 종료·새로고침 후 초안 복구 기능은 없다.

## 5. 공개 기능 요구사항

우선순위 `P0`는 개인정보·접수·기본 탐색 등 출시 차단 기준, `P1`은 주요 콘텐츠 경험이다. 각 항목의 수용 기준은 후속 변경에서도 유지한다.

### FR-NAV-01 공통 탐색과 푸터

**우선순위 P0 · 현재 수준 코드 확인**

- 상단 메뉴에서 홈, 정신, 소개, 공연·소식, 갤러리, 입단 안내, 후원·문의로 이동한다.
- 데스크톱 메뉴와 모바일 메뉴는 같은 정보 구조를 유지한다. 현재 위치와 선택 상태를 구분한다.
- 입단신청 CTA는 새 지원서로 연결한다. 푸터는 연락처·탐색·입단·후원·공식 SNS 중심으로 유지한다.
- 사이트 정보는 CMS 설정을 사용한다. 잘못된 주소나 빈 링크를 임의로 만들어 표시하지 않는다.

**수용 기준:** 마우스·키보드·터치로 주요 메뉴를 열고 닫을 수 있다. 선택 버튼·포커스 테두리가 컨테이너나 고정 헤더에 잘리지 않는다. 390px 화면에서 주요 버튼이 겹치지 않는다.

### FR-HOME-01 홈 콘텐츠와 최신 정보

**우선순위 P1 · 현재 수준 코드 확인**

- 공개 슬라이드, 팝업, 주요 문구, 소개, 입단 연결, 공연·공지, 정신, 갤러리, 후원 연결을 제공한다.
- 운영 데이터는 해당 리소스에서 가져오고, 홈의 표시용 문구는 `site_texts`와 홈 콘텐츠 모델로 관리한다.
- 기기별 홈 문구와 공통 공연·입단·미디어 데이터는 분리한다. 모바일 문구 수정이 실제 공연 데이터나 데스크톱 문구를 바꾸지 않는다.
- 일부 데이터 조회가 실패해도 성공한 컬렉션은 보존한다. 공연·공지·갤러리 실패를 실제인 것처럼 보이는 샘플 기록으로 대체하지 않는다.
- 팝업은 공개 여부와 게시 기간을 반영하고 닫기·표시 제어를 제공한다.

**수용 기준:** 데이터가 없으면 정직한 빈 상태를 보인다. CMS의 공개 순서와 승인된 기본 문구를 반영한다. 홈에서 공연 상세·입단지원·문의까지 이동할 수 있다.

**수용 기준:** 인물 사진의 비율을 보존한다. CMS 변경 시 기존 본문·이미지와 충돌하지 않는다. 지휘자 기본 경력 문구를 자동으로 연차 증가시키지 않는다.

**수용 기준:** 전체 목록에 현재 활동자가 누락되지 않는다. 한 사람이 파트 디렉터리에 중복 배치되지 않는다. 비공개 이름은 원본 대신 안전한 대체 표시를 사용한다.

### FR-HISTORY-01 연혁

**수용 기준:** 사진 없는 기록도 자연스럽게 표시한다. `aria-expanded`와 연결된 본문 패널을 제공한다. 연도·기록 수는 데이터로 계산한다.

### FR-CONCERT-01 공연 목록과 날짜

**우선순위 P1 · 현재 수준 코드 확인**

- 분류 선택은 실제로 열리고 선택되며 초기화가 가능해야 한다.

**수용 기준:** 검색 결과 없음과 등록된 공연 없음이 구분된다. 취소·마감 표기를 단순 예정 상태와 구분한다. 날짜·상태 분류의 현재 예외는 13절에서 별도 관리한다.

### FR-JOIN-03 모집 기간과 날짜 경계

**수용 기준:** 시간대가 다른 기기에서도 같은 모집 경계가 적용된다. 페이지를 열어둔 채 기간이 끝나도 신규 접수를 계속 허용하지 않는다.

### FR-JOIN-04 제출 확인과 재시도

**우선순위 P0 · 현재 수준 코드 확인**

작성 → 제출 전 확인 → 서버 제출 → 접수 완료 순으로 처리한다. 확인 단계에서 수정 화면으로 돌아갈 수 있다.

- 서버 설정 RPC `get_join_application_config`로 지원서 버전과 접수 조건을 확인한다.
- 제출 RPC `submit_join_application_v2`에 정규화된 응답과 `submission_id`를 전달한다.
- 연속 클릭을 차단하고 동일 요청 ID로 결과를 재확인한다. 서버가 명시적으로 성공을 반환한 경우에만 성공 화면을 보인다.
- 응답이 불명확하거나 실패하면 작성 내용을 유지하고 재시도를 안내한다.
- 이미 전송한 요청의 확인은 신규 접수와 구분한다. 접수 기간 밖이라고 기존 성공 여부 확인까지 막지 않는다.
- 이 중복 방지는 요청 단위다. 동일 인물이 새 요청 ID로 다시 신청하는 것까지 자동 차단하는 기능은 아니다.

**수용 기준:** 실패·권한 거부·버전 불일치를 성공으로 표시하지 않는다. 신청자의 원본 답변은 CMS 상태 변경 과정에서 덮어쓰지 않는다.

**수용 기준:** 미동의·잘못된 이메일 제출을 거부한다. 네트워크 오류로 입력이 사라지지 않는다. 자동 발송·답변 완료를 사실과 다르게 안내하지 않는다.

### FR-SUPPORT-01 후원약정

**우선순위 P0 · 현재 수준 기존 기능 코드 확인, 새 디자인은 후속 요구**

- 개인·기업 유형, 유형별 금액 옵션, 허용 시 직접 금액 입력을 제공한다.
- 이름·전화·이메일·양의 후원금액·개인정보 동의를 필수로 처리한다.
- 성별·생년월일·주소·예금주·약정 날짜·서명 등 추가 항목은 현재 선택 정보로 취급한다.
- 온라인 제출 사용 여부, 작성·동의·성공·인쇄 안내문과 연락처는 CMS 설정으로 관리한다.
- 현재 약정서에는 마우스·터치 서명, 지우기, 입력값을 반영한 인쇄 경로가 있다.
- 제출은 `support_pledges`에 약정 정보를 저장하는 동작이다. 결제나 출금을 실행하지 않는다.

**수용 기준:** 온라인 제출이 닫혔을 때 저장을 시도하지 않고 대체 안내를 제공한다. 금액과 동의 누락을 검사한다. 서명·인쇄의 실제 기기 동작은 별도 검증한다.

### FR-SPONSOR-01 후원사 노출

**우선순위 P0 · 현재 수준 코드 확인**

- 이름·표시명·분류·등급·설명·로고·URL·표시 순서를 관리한다.
- `is_visible=true`와 `consent_public=true`를 모두 만족해야 공개한다.
- 홈·후원 페이지·푸터의 노출 위치 설정을 구분한다.
- 등록된 후원사가 없으면 가상의 로고나 기관명을 넣지 않는다.

**수용 기준:** 공개 여부만 켜고 공개 동의가 없는 후원사는 표시되지 않는다. 로고는 비율을 유지한다.

### FR-LOCATION-01 연락처와 오시는 길

**우선순위 P1 · 현재 수준 코드 확인**

- 주소, 전화, 팩스, 이메일, 교통·주차 안내, 장소 사진을 설정 값에 따라 표시한다.
- 네이버·카카오 지도 링크와 허용된 지도 임베드를 사용한다.
- 임베드가 없거나 실패해도 주소와 지도 링크를 이용할 수 있어야 한다.

**수용 기준:** 연락처 라벨과 값이 정렬된다. 빈 값 때문에 불필요한 줄이나 작동하지 않는 버튼이 생성되지 않는다.

### FR-CMS-01 인증과 권한

**우선순위 P0 · 현재 수준 코드 확인**

- Supabase Auth 인증과 `profiles.role='admin'` 확인을 모두 통과해야 관리자 화면을 사용한다.
- 미로그인은 로그인으로 이동하고, 권한 없음·설정 없음·인증 확인 실패를 구분한다.
- 같은 관리자의 토큰 갱신을 전체 화면 재로딩으로 처리해 작성 중인 내용을 잃지 않는다. 로그아웃·다른 사용자로 전환·권한 회수는 다시 차단한다.
- 관리자 계정 생성은 운영자가 관리하는 절차이며 공개 회원가입 기능을 제공하지 않는다.

**수용 기준:** 주소 직접 입력만으로 CMS에 접근하지 못한다. UI 보호를 통과하더라도 DB·Storage의 RLS가 최종 권한을 검사한다.

### FR-CMS-02 콘텐츠 편집과 저장

**우선순위 P0 · 현재 수준 코드 확인**

- 목록형 콘텐츠는 검색·필터·생성·편집·삭제·공개 상태를 리소스 특성에 맞게 제공한다.
- 단일 설정은 별도 편집 양식에서 저장한다. 필수값·형식 오류는 저장 전 검사한다.
- 새 저장 시도에서는 이전 성공·오류 메시지를 정리하고 이번 시도의 결과만 표시한다.
- 저장되지 않은 변경에 대해 이동 경고를 제공하는 기존 편집 패턴을 유지한다.
- 삭제는 정확한 대상 확인과 실패 안내를 제공한다. 삭제 후 되돌리기나 버전 복원이 구현되어 있다고 가정하지 않는다.
- 저장 후 해당 공개 데이터 캐시를 무효화한다. 다른 탭·다른 사용자의 화면이 실시간 동기화되는 것은 현재 보장하지 않는다.

**수용 기준:** 저장 실패가 성공 메시지와 동시에 보이지 않는다. 저장 후 새로 조회해 변경 값을 확인한다. 취소가 실제 저장이나 삭제를 유발하지 않는다.

### FR-CMS-03 홈 기기별 문구

**우선순위 P1 · 현재 수준 로컬 코드 확인**

- 데스크톱·태블릿·모바일 문구 편집을 구분하고 각 기기의 초안·저장 상태·미리보기를 보여준다.
- 선택 기기의 저장이 다른 기기의 미저장 초안을 지우지 않는다.
- 공통 운영 데이터는 각 전용 메뉴에서 관리한다. 문구 편집으로 공연 날짜, 모집 기간, 사진 DB를 복제하지 않는다.
- 사용할 수 없는 기기별 문구는 승인된 기본값으로 해석한다. 빈 값이 다른 기기의 임의 문구를 끌어오지 않도록 현재 해석 계약을 유지한다.

**수용 기준:** 기기 전환·저장·기본값 복원 후 변경 범위가 명확하다. 운영 CMS에서의 실제 저장·새로고침 확인은 별도 실행한다.

### FR-CMS-04 접수 업무 관리

**우선순위 P0 · 현재 수준 코드 확인**

| 업무 | 상태 선택지 | 관리자 수정 범위 |
| --- | --- | --- |
| 입단지원 | 신규 `new`, 연락 완료 `contacted`, 오디션 안내 `audition_guided`, 보류 `on_hold`, 처리 완료 `done` | `status`, `admin_notes`, `is_archived` |
| 문의 | 새 문의 `new`, 확인 중 `reviewing`, 답변 완료 `answered`, 보류 `on_hold`, 보관 `archived` | 상태·내부 메모·답변 및 관련 처리 메타데이터 |
| 후원약정 | 신규 `new`, 처리 중 `in_progress`, 완료 `done` | 처리 상태 |

현재 상태 선택지는 업무 분류이며 순차 이동을 강제하는 워크플로 엔진은 아니다. 입단지원의 보관 여부는 처리 상태와 별도로 유지한다. 문의의 과거 `in_progress`, `done` 값은 현재 라벨과 호환 처리한다.

**수용 기준:** 답변 완료로 저장할 때 답변 내용이 비어 있으면 거부한다. 지원자·후원자가 제출한 원본 답변을 상태 수정 payload에 섞지 않는다. 접수 기록의 공개 전환 스위치를 제공하지 않는다.

### FR-CMS-05 이미지와 파일

**우선순위 P0 · 현재 수준 코드 확인**

- 공개 이미지는 `site-images` Storage와 기존 업로더 패턴을 사용한다.
- 기본 콘텐츠 이미지는 JPG·PNG·WebP, 기본 크기 제한은 5MB다. 브랜드용 SVG는 허용된 업로드에서만 사용하며 기본 제한은 2MB다. 개별 업로더 설정과 실제 버킷 정책도 함께 적용한다.
- 파일명은 충돌을 줄이는 별도 이름으로 저장하고 일반 업로드는 기존 파일을 자동 덮어쓰지 않는다.
- 기존 입단지원 첨부는 공개 이미지와 구분하고 관리자용 만료 링크로 열람한다. 새 v2 양식은 첨부를 수집하지 않는다.
- 파일 확장자·MIME의 프론트 검사만으로 보안 검증이 완료되었다고 판단하지 않는다.

**수용 기준:** 허용하지 않는 형식·크기·권한 오류가 사용자에게 설명된다. 비공개 첨부를 영구 공개 URL로 바꾸지 않는다. 이미지 교체가 다른 콘텐츠에서 쓰는 원본을 무단 삭제하지 않는다.

### 7.2 데이터 관계

- 사진·영상·포스터의 `related_concert_id`는 공연 자료와 연결한다. 연관 관계가 있다고 해서 모든 공개 화면이 자동으로 관계 자료를 합쳐 표시하는 것은 아니다.
- 공연 상세의 대표 포스터는 현재 `concerts.poster_url`을 사용한다. 별도 포스터 아카이브 등록만으로 대표 포스터가 교체된다고 가정하지 않는다.
- v2 신청은 `join_info_id`로 모집 안내와 연결하고 `submission_id`로 동일 요청을 구분한다.
- 운영 콘텐츠에는 리소스별로 공개 여부·순서·작성일·수정일을 적용한다. 없는 필드를 모든 테이블에 있다고 가정하지 않는다.

### 7.3 공개 조회와 CMS 반영

공개 화면은 `usePublicData` 계열 훅 → `publicData` → Supabase 조회 경로를 우선한다. 관리자 화면은 `useCrudList`·`useCrudItem` → `cms`와 `storage`를 사용한다.

현재 공개 훅 캐시 TTL은 60초이며, 같은 요청을 중복 실행하지 않도록 공유한다. CMS 저장 후 동일 실행 환경의 캐시를 무효화한다. TTL이 있다고 해서 열린 모든 페이지를 60초마다 자동 새로고침하는 것은 아니다.

기본 소개·인물·장소 일부에는 승인된 레거시 fallback이 남아 있다. 실제 공연·공지·갤러리 컬렉션 fallback은 빈 배열을 사용한다. 기본 콘텐츠와 운영 데이터의 경계는 변경 시 검토한다.

### 7.4 외부 서비스

- Supabase: 인증, PostgreSQL 데이터, RLS, 이미지·기존 첨부 Storage.
- YouTube: 갤러리 영상과 재생 링크.
- 네이버·카카오 지도: 외부 지도와 장소 안내.
- 외부 티켓·신청 URL: 공연별 CMS 값으로 연결.
- Figma: 디자인 승인과 비교 기준. 시안이 있다고 코드·CMS에 적용된 것으로 간주하지 않는다.

## 8. 개인정보와 보안 요구사항

### NFR-SEC-01 공개와 관리자 경계

- RLS와 서버 권한을 보안 기준으로 삼는다. 프론트에서 버튼을 숨기는 것만으로 접근을 통제하지 않는다.
- 공개 콘텐츠도 직접 URL·API 요청에서 비공개 레코드가 반환되지 않아야 한다.
- 청소년 단원은 공개 동의에 따른 표시 이름만 노출하고, 원본 이름·사진·설명이 응답에 섞이지 않도록 한다.
- 문의·신청·후원약정은 익명 목록 조회를 금지한다. 현재 사용자 권한과 무관하게 공개 페이지의 안전한 응답 계약을 유지한다.
- 비공개 파일은 만료 링크와 관리자 권한으로 보호한다.

### NFR-SEC-02 입력과 비밀정보

- Supabase 비밀키, 관리자 비밀번호, Figma 토큰, DB 비밀번호를 코드·문서·클라이언트 번들에 넣지 않는다.
- 프론트에서는 공개용 키만 사용하며 `service_role` 권한을 넣지 않는다.
- 외부 URL은 스킴과 허용된 공급자 규칙을 검사한다. CMS 텍스트를 임의 HTML 실행 권한으로 취급하지 않는다.
- 접수 필수값과 동의는 클라이언트와 서버 계약에 맞춰 검증한다. 서버 오류나 마이그레이션 미적용을 성공으로 대체하지 않는다.
- 기존 허니팟은 보조 방어일 뿐이다. 서버 속도 제한·봇 대응 전체가 구현되어 있다고 주장하지 않는다.

### NFR-SEC-03 운영 정책

개인정보 수집 목적·항목·보유 기간·삭제 절차·열람 책임자를 운영자가 확정해야 한다. 미성년자 동의와 보호자 연락 처리, 후원 서명 보관, 사진 공개 동의도 검토 대상이다. 이 PRD는 법률 적합성 인증이나 확정된 보존 기간을 대신하지 않는다.

권한 설계 기준은 [Supabase RLS 공식 문서](https://supabase.com/docs/guides/database/postgres/row-level-security)를 참고한다. 서비스 역할처럼 RLS를 우회할 수 있는 권한은 클라이언트에 제공하지 않는다.

## 9. UX 디자인과 접근성

### 9.1 시각적 방향

- 프로젝트 기본 방향은 Deep Navy, Warm Gold, Ivory 계열이다. 현재 승인된 화면에는 밝은 종이색 바탕, 절제된 주황 구분선, 버건디 강조, 어두운 푸터가 함께 사용된다.
- 이후 변경은 실제 적용된 화면과 승인된 시안을 함께 기준으로 삼는다. 전 페이지를 무조건 검정이나 새로운 카드 디자인으로 통일하지 않는다.
- 사진·포스터가 주인공인 화면에서는 장식이 콘텐츠보다 앞서지 않도록 한다.
- 인물 사진·포스터는 원본 비율 보존을 우선하고, `cover`는 분위기용 배경에 제한한다.
- 한국어 날짜와 핵심 동작 이름은 장식용 영문보다 먼저 읽혀야 한다.
- 인명, 승인된 약력, 모집 조건, 운영 수치는 근거 없이 수정하거나 생성하지 않는다.

### 9.2 조작과 상태

- 버튼처럼 보이는 요소는 실제 조작 결과와 선택 상태가 있어야 한다. 단순 장식은 조작 요소처럼 표현하지 않는다.
- hover 효과는 키보드 포커스와 터치 대안을 가진다. 마우스를 올려야만 본문이 나타나는 방식에 의존하지 않는다.
- 로딩·빈 데이터·검색 결과 없음·네트워크 오류·권한 없음·저장 중·성공을 구분한다.
- 실패하면 입력·선택을 가능한 범위에서 유지하고 재시도·수정·복귀를 제공한다.
- 고정 헤더, 탭 컨테이너, 모달 때문에 제목·선택 버튼·날짜가 가려지지 않아야 한다.

### 9.3 접근성 수용 기준

- 기본 목표는 WCAG 2.2 AA 수준의 접근성을 고려한 설계이며, 현재 사이트 전체가 인증·감사 완료되었다는 뜻은 아니다.
- 핵심 버튼과 모바일 조작 영역은 프로젝트 기준 최소 44×44 CSS px를 목표로 한다. 이 기준을 WCAG AA의 일률적인 최소값이라고 표현하지 않는다.
- 일반 본문 대비는 4.5:1, 큰 글자는 3:1을 기준으로 확인한다.
- 키보드 탐색, 명확한 포커스, 입력 라벨·오류 연결, 상태 알림, 의미 있는 제목 구조를 제공한다.
- 확대·모달은 ESC 닫기, 포커스 관리와 원래 조작 지점 복귀를 확인한다.
- `prefers-reduced-motion`에서는 장식 애니메이션을 줄이거나 제거한다. 정지 상태에서도 모든 핵심 정보와 동작을 이용할 수 있어야 한다.
- 390px·768px·1440px, 글자 확대, 긴 텍스트, 모바일 키보드 상황에서 넘침과 겹침을 확인한다.

기준: [W3C WCAG 2.2 빠른 참조](https://www.w3.org/WAI/WCAG22/quickref/). 최종 적합성 판단에는 실제 화면과 보조기술 검증이 필요하다.

### 10.2 로딩과 성능

- 라우트 지연 로딩과 데이터 로딩 상태를 구분한다.
- 같은 공개 요청을 공유하고 성공한 데이터를 캐시한다. 캐시 때문에 실패 데이터나 비공개 변경이 무기한 남지 않아야 한다.
- 이미지는 적정 해상도와 지연 로딩을 사용하고, 대표 이미지 우선순위를 별도로 설정한다.
- 대량 목록의 서버 페이지네이션·무한 스크롤이 전 리소스에 구현되었다고 간주하지 않는다. 데이터 증가 시 조회량과 렌더링을 측정한다.
- LCP·INP·CLS와 실제 저사양 모바일 성능은 후속 측정 항목이다. 측정하지 않은 성능 점수·가용률을 PRD의 달성 결과로 쓰지 않는다.

### 10.3 SEO와 배포

- `SeoHead`에서 페이지 제목, 설명, canonical, OG, Twitter 메타, 필요한 JSON-LD를 설정한다.
- 공연 상세는 날짜가 유효할 때 Event 구조화 데이터를 구성한다.
- 현재 메타 갱신은 클라이언트 방식이다. 검색·SNS 미리보기의 실제 수집 성공을 자동 보장하지 않는다.
- 정적 배포 시 직접 진입·새로고침 경로가 SPA로 처리되도록 호스팅 설정을 확인한다.
- 공개 샘플·관리자·신청 화면의 검색 노출 정책, 실제 도메인, sitemap·robots 운영은 배포 전 확인한다.
- Vite 개발 서버·preview 명령을 운영 서버로 간주하지 않는다. [Vite 정적 배포 문서](https://vite.dev/guide/static-deploy)를 배포 절차의 참고 기준으로 사용한다.

### 10.4 데이터 변경과 복구

- 마이그레이션 전 실제 스키마·정책과 기존 데이터 호환성을 확인한다.
- 이미 적용된 `20260908_join_application_v2.sql`은 기존 운영 기록에 따라 무조건 재실행하지 않는다.
- 기본 `schema.sql`만으로 모든 최신 테이블·컬럼이 준비된다고 가정하지 않는다.
- 기존 문의·지원서·약정·파일을 보존하고, 운영 데이터를 QA용으로 생성·삭제하지 않는다.
- 백업·복원 주기, 담당자, 복원 목표 시간은 운영 결정 사항이다. 백업이 구성되었다고 확인 없이 기록하지 않는다.

| P1 | 공연 날짜 갱신 | 목록의 오늘 값은 마운트 시 계산. 자정을 넘어 열린 탭에서 자동 재분류할지 결정 필요 |
| 구현 | 관리자 집계 상태 | 9/17: `new`, `contacted`, `audition_guided`, `on_hold` 중 보관하지 않은 지원서를 집계. 한 요청의 실패가 전체 집계를 지우지 않도록 보완하고 테스트 |
| P1 | 공연 필터 복원 | 기간 외 검색·분류·연도는 URL에 저장하지 않음. 상세 복귀 시 유지 범위를 정할 필요 |

| P1 | CMS와 기본 콘텐츠 경계 | 일부 소개·프로필·연혁·지도·배경 이미지는 기본값 또는 코드 자산 사용. 모든 텍스트·사진이 CMS 완전 제어라고 표현하지 않음 |
| P1 | 배포와 검색 노출 | 실제 도메인, SPA rewrite, 샘플 경로 노출, 클라이언트 메타 수집, robots·sitemap 정책 확인 필요 |

‘구현’ 표기만 9/17 변경 증거를 반영했다. 나머지는 기존 차이·확인 과제이며, 실제 검증 범위는 CMS 개선 결과에서 구분한다. 특히 모든 문구의 편집 연결, Storage 비공개 초안 경계, 운영 배포 헤더까지 완료되었다고 표현하지 않는다.

### 13.1 CMS 개선 요구 계약

| ID | 계약 | 검증 기준 |
|---|---|---|
| CMS-EDIT-01 | 공통/모바일/태블릿/PC별 문구·서체·크기·색을 분리 | 선택하지 않은 기기/화면 및 override 없는 기존 디자인 불변 |
| CMS-EDIT-02 | 임시저장과 게시의 실제 쓰기 분리 | 저장으로 public 게시본이 바뀌지 않고 게시 시 기대 버전 일치 확인 |
| CMS-EDIT-03 | 미리보기와 실제 접수 분리 | 출처/source/nonce/문서 검증, 지원서·문의·약정의 실제 제출 차단 |
| CMS-EDIT-04 | 실패해도 입력 유지 | 업로드 실패/저장 경합/뒤로가기/중복 클릭/요청 중 추가 입력 테스트 |
| CMS-INTAKE-01 | 원문·서명·동의·인쇄 보존 | 관리자는 상태·메모만 변경. 옛 약정에 현재 원문을 소급 대입하지 않음 |
| CMS-INTAKE-02 | 서버 접수 검증·재시도·용량 보호 | UI 우회 입력 거부, 같은 요청 재시도와 다른 내용 재사용 구분 |
| CMS-DESIGN-01 | CMS만 Quiet Workspace 적용 | Figma 18개 대표 상태/10차 검토, 관리자 범위 스타일, public 디자인 변경 금지 |
| CMS-SEC-01 | 민감 원본·초안 비공개 | 익명 원본 조회 차단, 최소 필드 public API. Storage 경계는 별도 미완료 |
| CMS-OPS-01 | 초보 운영자의 작업 맥락 | 실제 메뉴/동작 이름의 한국어 사용 안내, 저장·게시·원본 관리 차이 명시 |
