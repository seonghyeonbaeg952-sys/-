# 공개 접수 경계 보완 — 진행 기록

## 변경 경계

- 문의·후원약정은 직접 테이블 INSERT 대신 검증된 전용 RPC를 사용한다.
- 필수 항목, 동의, 문자열 길이·타입·예상 키, 이메일·전화번호·날짜·금액을 서버에서 확인한다.
- 서명은 원본 PNG 문자열을 보존하며 크기와 컨테이너를 검사한다. 서명자의 신원이나 법적 진정성을 증명하는 기능은 아니다.
- 같은 UUID와 같은 답변의 재시도는 이미 접수한 결과를 반환한다. 내용이 달라진 재사용은 거부한다.
- 한 시간 이동 구간의 접수량을 종류별·연락처별로 제한한다. 기본값은 종류별 100건, 정규화한 연락처별 5건이며 관리자가 조정할 수 있는 RLS 보호 설정 테이블을 둔다. IP 인증이나 네트워크 DDoS 방어로 과장하지 않는다.
- 후원 접수 중단 설정은 서버의 현재 공개 안내에서 확인한다. 접수 당시 안내 원문은 서버 생성 스냅샷으로 보존한다. 기존 약정 행은 변경하거나 소급 추정하지 않는다.
- 입단 v2의 기존 입력 검증·모집 기간·멱등성을 유지하고 새 접수만 용량 제한을 적용한다.
- 사용하지 않는 v1 입단 업로드 구현을 제거했다. 예전 import 경로는 새 입단 안내로 유도하는 실패 안전 응답만 제공한다. 과거 첨부 파일은 삭제하지 않았다.

## 적용 순서와 확인

2026-09-17, 기존 권한을 유지한 상태에서 추가 RPC/비공개 영수증 저장소를 먼저 설치했다. 서버 계약 테스트를 트랜잭션 rollback으로 검증한 뒤 문의·약정 양식을 연결했다. 이후 직접 INSERT 권한과 관련 공개 INSERT 정책만 제거했다. 실제 운영 행의 삭제는 없다.

Supabase SQL Editor 결과: `contact_direct_blocked`, `pledge_direct_blocked`, `contact_rpc_ready`, `pledge_rpc_ready` 모두 true.

SQL Editor 검증 결과: `PASS: intake contract; synthetic rows and privilege changes rolled back`.

검증한 경우: 정상 문의/약정, 원문 보존, 같은 요청 재시도, 변경된 요청 ID 거부, 관리자 필드 주입, 동의 누락, 잘못된 이메일, 과대 본문, null 필수값, 연락처별 한도, 한도 도달 후 기존 요청 재시도, 안내 ID 불일치, 접수 중단, 실패 요청의 한도 미소모, 잘못된 날짜·서명, 정상 PNG, 직접 INSERT 거부.

로컬 명령:

- `node --test src/lib/publicIntakeIntegration.test.mjs`: 기존 직접 INSERT 경로에서 3개 실패를 확인한 뒤 전용 RPC 연결 후 통과.
- `node --test src/components/contact/SupportPledgeForm.test.mjs`: 재시도 ID 누락 실패를 먼저 확인한 뒤 9개 통과. 원문·서명·인쇄 회귀 포함.
- 접수 모델/API/연결/약정 폼 묶음 21개 통과.
- `pnpm test`: 297개 통과.
- `pnpm exec tsc -b`, `pnpm lint`: 통과.
- PGlite 격리 계약 테스트 통과. 운영 PostgreSQL 검증을 대체하는 것으로 취급하지 않음.

## 남은 검증 / 전체 작업 미완료

- 별도 실제 세션 동시 제출, 시간 경계 및 전체 용량 제한, 입단 v2 용량 회귀를 추가 검증해야 한다.
- 관리 화면의 접수량 설정·접수 당시 약정 스냅샷·인쇄 흐름은 연결했다. 390px 설정 저장/잘못된 수치/입력 보존과 768px 약정 상세·print CSS emulation을 격리된 합성 transport에서 확인했다. 운영 한도나 실제 약정 행은 바꾸지 않았다.
- Storage 공개/비공개 자산 경계 보완은 이 변경의 해결 범위가 아니다.
- 테스트는 실제 접수·실물 인쇄·모바일 실기기를 대신하지 않는다.
- SQL Editor로 적용했으므로 Supabase CLI migration history는 별도 대조가 필요하다.
